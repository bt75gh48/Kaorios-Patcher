# Decisions

## 2026-11-20

- Ported the full 2.0.6.2 patch surface into `domain/actions/smali/` (`ActivityThreadPatch`, `ComputerEnginePatch`, `SystemServerPatch`, `KeystorePatch`, `InstrumentationPatch`, `AppPkgManagerPatch`, `NameValueCachePatch`, `InstallerSourcePatch`, `PayloadAbiVerifier`, `SmaliOps`, `TargetPatcher`, `TreeVerifier`) and routed `KaoriosToolbox2036Script` through `TargetPatcher` so both the CLI and the app share one patch/verify contract.
- Reused Python's fail-closed layout rules in `ActionRunner` instead of copying its staged-tree rewrite. Duplicate class locations are rejected via `SmaliEngine.findAllForClass` (`check(size <= 1)`), symlinked targets are rejected with `Files.isSymbolicLink`, and any original file whose bytes changed between preflight and commit aborts the whole commit with no writes. Rejected the staged-tree rewrite: the Kotlin runner already has snapshot→commit semantics, so a full staging tree would add risk without adding safety to the op-keyed model.
- Put payload ABI and tree verification in `afterCommit` (`KaoriosToolbox2036Script`), not before commit. The payload dex only exists after `ImportDexUseCase` runs, so verifying earlier would have nothing to verify against. Caller files are copied into a temp staging root first (`stageCallers`) so the verifier sees callers only, matching Python's `staged_root`; the temp dir is deleted in a `finally`. A failure here marks the script FAIL without rollback, because the source files are already committed — same as Python's post-write behaviour.
- Added `TreeVerifier.verifyActivityThread` as a deliberately narrow check. Python's `run_directory_verifiers` framework branch only finds `ActivityThread.smali` and runs that one verifier; it does not require the `KaoriosHook` callee or the eight AdvancedPolicy classes. Those belong to the standalone CLI's `verify_root`, so `verifyFramework` stays separate rather than being reused here.
- Rejected deriving the Android generation from the workspace to gate mode 2/3. `Build$VERSION.smali` does not carry a literal SDK level (`SDK_INT` comes from `SystemProperties.getInt` at runtime), so any detection would be a guess. Python's `process_files` also never uses `mode` to pick targets — the mode is a scope selector plus a CLI-level guard. The app therefore exposes mode as an explicit choice with the Android-17 note shown in the picker, and the Build patchers stay fail-closed on their own anchors (`TIME:J not found`, missing `Build$VERSION` fields), which is what actually protects an A13–16 ROM.
- Made the picker default to `PatchMode.ORIGINAL` (mode 1) instead of the previously hardcoded `PatchMode.ALL`, matching the Python default. A hooks-only script run under mode 2/3 now fails before any write instead of silently filtering every op out, running `afterCommit`, and reporting success.
- Kept the existing app version and did not add release signing. No device validation was possible on this machine (no Android SDK, no connected device), so CI compiles are the only gate for the Android-dependent files.

## 2026-11-19

- Fixed the `Settings$NameValueCache` hook ABI in `HideDevOptionsScript.kt` from a boolean result to the `String` result expected by the 2.0.6.2 patch contract. The injected block now uses `move-result-object` and returns the hook value directly.
- Added `.github/workflows/build.yml` to build debug and release APKs on pushes, pull requests, and manual dispatch, then upload both APK outputs as workflow artifacts.
- Kept release signing out of CI because the repository has no configured signing secret or signing configuration. The release artifact is therefore unsigned; no key material is added to the repository.
- Kept the existing app version and broader patch scope unchanged. The request identified a concrete ABI incompatibility; expanding the patch surface without source fixtures or device validation would be speculative.
