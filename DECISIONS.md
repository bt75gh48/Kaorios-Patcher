# Decisions

## 2026-11-20

- Restructured the Actions list into the order the user specified: Toolbox 2.0.6+ → Remove Aosp/Custom rom Hooks → Remove invoke-custom (A15) → Remove Build Flag (Android 17) → Dex Redivision → Update Dex → Hide Dev → Hide App → Spoof Installed Source → Disable Secure Flag. The order is enforced in the domain layer, not just in the picker.
- Replaced the four-value `ScriptPriority` (`TOOLBOX`, `REMOVE`, `REBUILD`, `UPDATE`) with one value per script. The old enum could not produce the requested order: `sortForExecution` sorts by `priority.order`, and every `REMOVE` entry shared order `1`, so Kotlin's stable sort would have fallen back to the registry's declaration order. Declaring the entries in the right order and leaving the enum alone would have looked correct and broken the moment a caller passed a differently-ordered selection — the test harness exercises exactly that (reversed input). Ten distinct priorities make the order a property of each script rather than of the list literal.
- Deleted `KaoriosToolbox109Script` and `Toolbox109Config`. Rejected keeping 1.0.9 selectable-but-hidden: the two toolbox scripts share `ActionState.SCRIPT_ID_TOOLBOX_2036`-adjacent tag plumbing in `FileBrowserViewModel`, so a hidden third path would still have to be maintained and would still be able to write `ActionState`. Removing it also let `finishTagSelection` collapse its two-way branch to a single `when` on `SCRIPT_ID_UPDATE_KAORIOS_DEX`.
- Raised both `DEFAULT_TAG` constants from `V2.0.4` to `V2.0.6` in `Toolbox2036Config` and `UpdateKaoriosDexConfig`, so the prefilled tag matches the only toolbox release the picker now offers.
- Split the two halves of `ComputerEnginePatch` into separate scripts: `HideAppScript` (only `shouldFilterApplication`) and `SpoofInstalledSourceScript` (only the installer-provenance methods). `ComputerEnginePatch` gained `patchVisibilityOnly` / `patchInstallerOnly` plus matching verifiers so each script verifies only its own half. Rejected making both scripts call the combined `patch()`: that would have made Hide App also inject the installer hook, so ticking one box would silently apply two patches.
- Kept `ComputerEnginePatch.patch()` (both halves) and routed `KaoriosToolbox2036Script` through `TargetPatcher` unchanged, so the toolbox script still applies the full 2.0.6.2 services patch. Selecting both Toolbox and Hide App / Spoof is therefore allowed. Rejected blocking that combination in the picker: `patchVisibility` and `InstallerSourcePatch.patch` both return `changed = false` when their hook is already present, so the second application is a no-op rather than a double hook. The harness confirms idempotence byte-for-byte.
- Extracted the two Build-field ops out of `HideDevOptionsScript` into `RemoveBuildFlagScript` (Android 17). `HideDevOptionsScript` now holds only its 18 Settings ops. Rejected leaving the Build ops in place and adding a separate script: that would have patched `Build` twice when both were selected.
- Made `RemoveBuildFlagScript`'s absence from mode 1 explicit in the picker instead of letting it fail at run time. All of its ops are `PatchMode.BUILD`, and `ActionRunner` treats "no op belongs to this mode" as a failure that breaks the whole run loop — so in the default mode 1 the script would have aborted every script ordered after it, including Hide Dev / Hide App / Spoof / Disable Secure Flag. The picker now hides scripts that have no op for the selected mode. Rejected making the runner skip instead of fail: that error is exactly what catches a hooks-only script run under mode 2/3, and weakening it would trade a visible bug for a silent no-op.
- Left `RemoveInvokeCustomScript` on its own priority rather than merging it with `RemoveHooksScript`. Both are `ScriptGroup.REMOVE`, but the requested order puts invoke-custom removal after AOSP hook removal, and they touch different files.

### Earlier the same day

- Fixed the tree-verifier gate in `KaoriosToolbox2036Script.afterCommit`. The three checks were `File(staged, "android/app/ActivityThread.smali").isFile` and two siblings, but `stageCallers` writes each target under its workspace relative path, which is `<classesN>/<internal path>` — so all three conditions were always false and the framework, services and systemserver verifiers never ran. Rejected keeping a path-shaped check at all: the dex index in `classesN` is not knowable ahead of time, so any literal path is a guess. `stageCallers` now returns the set of target filenames it staged, and the gates test membership in that set — which is what Python's `run_directory_verifiers` actually does (`"ActivityThread.smali" in processed_filenames`). `TreeVerifier.matches` already resolves by path suffix, so it finds the nested files unchanged.
- Ported the full 2.0.6.2 patch surface into `domain/actions/smali/` (`ActivityThreadPatch`, `ComputerEnginePatch`, `SystemServerPatch`, `KeystorePatch`, `InstrumentationPatch`, `AppPkgManagerPatch`, `NameValueCachePatch`, `InstallerSourcePatch`, `PayloadAbiVerifier`, `SmaliOps`, `TargetPatcher`, `TreeVerifier`) and routed `KaoriosToolbox2036Script` through `TargetPatcher` so both the CLI and the app share one patch/verify contract.
- Reused Python's fail-closed layout rules in `ActionRunner` instead of copying its staged-tree rewrite. Duplicate class locations are rejected via `SmaliEngine.findAllForClass` (`check(size <= 1)`), symlinked targets are rejected with `Files.isSymbolicLink`, and any original file whose bytes changed between preflight and commit aborts the whole commit with no writes. Rejected the staged-tree rewrite: the Kotlin runner already has snapshot→commit semantics, so a full staging tree would add risk without adding safety to the op-keyed model.
- Put payload ABI and tree verification in `afterCommit` (`KaoriosToolbox2036Script`), not before commit. The payload dex only exists after `ImportDexUseCase` runs, so verifying earlier would have nothing to verify against. Caller files are copied into a temp staging root first (`stageCallers`) so the verifier sees callers only, matching Python's `staged_root`; the temp dir is deleted in a `finally`. A failure here marks the script FAIL without rollback, because the source files are already committed — same as Python's post-write behaviour.
- Added `TreeVerifier.verifyActivityThread` as a deliberately narrow check. Python's `run_directory_verifiers` framework branch only finds `ActivityThread.smali` and runs that one verifier; it does not require the `KaoriosHook` callee or the eight AdvancedPolicy classes. Those belong to the standalone CLI's `verify_root`, so `verifyFramework` stays separate rather than being reused here.
- Rejected deriving the Android generation from the workspace to gate mode 2/3. `Build$VERSION.smali` does not carry a literal SDK level (`SDK_INT` comes from `SystemProperties.getInt` at runtime), so any detection would be a guess. Python's `process_files` also never uses `mode` to pick targets — the mode is a scope selector plus a CLI-level guard. The app therefore exposes mode as an explicit choice with the Android-17 note shown in the picker, and the Build patchers stay fail-closed on their own anchors (`TIME:J not found`, missing `Build$VERSION` fields), which is what actually protects an A13–16 ROM.
- Made the picker default to `PatchMode.ORIGINAL` (mode 1) instead of the previously hardcoded `PatchMode.ALL`, matching the Python default. A hooks-only script run under mode 2/3 now fails before any write instead of silently filtering every op out, running `afterCommit`, and reporting success.
- Kept the existing app version and did not add release signing. No device validation was possible on this machine (no Android SDK, no connected device), so CI compiles are the only gate for the Android-dependent files.

## 2026-11-19

- Fixed the `Settings$NameValueCache` hook ABI in `HideDevOptionsScript.kt` from a boolean result to the `String` result expected by the 2.0.6.2 patch contract. The injected block now uses `move-result-object` and returns the hook value directly.
- Added `.github/workflows/build.yml` to build debug and release APKs on pushes, pull requests, and manual dispatch, then upload both APK outputs as workflow artifacts.
- Kept release signing out of CI because the repository has no configured signing secret or signing configuration. The release artifact is therefore unsigned; no key material is added to the repository.
- Kept the existing app version and broader patch scope unchanged. The request identified a concrete ABI incompatibility; expanding the patch surface without source fixtures or device validation would be speculative.
